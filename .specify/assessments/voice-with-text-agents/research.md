## Prior Art

### Current application: shared execution does not mean shared conversation context

- **Voice delegates to the application, not to an agent selected in the Live event.** The adapter starts GPT-Live with client delegation. Its accepted delegation object contains an ID, type and `target: client`, not a destination agent. The voice endpoint obtains task text from correlated input-transcript fragments; the executor subsequently chooses the agent at the current session slot's `active_agent_id`. This supports the reported "latest active agent" behavior, but more precisely identifies it as the conversation's retained active position, not a global last-used agent across conversations. [source: S2, S3, S4] (confidence: high for code behavior; cited)
- **The working agents do have some history, but not the entire voice conversation.** The executor separately retains `_history` and `_transcripts`. Model execution receives `_history` plus the current accepted task, then records the generated answer in `_history`. Ordinary input/output transcript deltas populate `_transcripts`, not that model input; the special exception is the opening spoken greeting. Therefore, delegated-task history is not equivalent to everything the caller and speaking model have said, including the speaking model's eventual paraphrases. [source: S3] (confidence: high for the inspected data flow; cited)
- **The clarity check is deliberately narrower than conversation understanding.** Before executing correlated voice input, `_clear_task` asks the active agent whether the exact fragments contain a self-contained request, without passing `_history`; it explicitly prohibits filling in missing words or rewriting the task. The correlator permits at most 4 KiB of ordered verified fragments and requires the delegation offset to be within two seconds of the last fragment. Conversational follow-ups whose meaning depends on earlier exchanges are consequently a relevant unverified case, not evidence that the present clarity check already resolves context-dependent intent. [source: S3, S4, S5] (confidence: high for constraints; medium for relevance to the reported failure; cited inference)
- **Handover exists in both modalities and remains application-authorized.** The shared executor exposes role-specific routing, peer-handover and community-transfer tools. Policy validates the source agent/epoch and directed graph before changing ownership. Agents SDK agents are built with `handoffs=[]`; SDK-native handoff behavior is not the application's current routing mechanism. Existing tests exercise shared execution and allowed transitions. [source: S3, S6, S8, V1] (confidence: high; cited)
- **Some context loss on agent change is intentional, including in text.** On an agent-epoch change, the executor clears its prior history. Ordinary-agent transfers pass only relationship-allowed `request_summary` and `transfer_reason`; the initial lifecycle-routing path retains the current task. A test explicitly asserts that the destination sees the permitted summary but not source-only detail or the source agent's prompt. An unrestricted "entire progress to every agent" interpretation would change this boundary, rather than merely repair missing synchronization. [source: S3, S6, S8, S11] (confidence: high; cited)
- **Voice handover also replaces the speaking session.** Policy retires and closes the old Live session before continuing with a new generation. The continuation starts a fresh session with instructions; the adapter's startup event supplies no prior `input` history. Current composition uses the active agent's prompt plus a delegation suffix. Thus, the continuation path inspected here does not seed the new Live session with the earlier spoken conversation. Existing tests verify socket retirement and delivery to the new segment, not preservation of the whole spoken dialogue. [source: S2, S6, S8, V1] (confidence: high for inspected behavior; cited)
- **Text has a distinct persistence precedent.** The text service loads owner-keyed completed turns and active agent/community position, revalidates the position, restores executor history and saves successful turns. Voice does not use this store. Text continuity is therefore already supported between requests, but is still subject to the agent-change reset and does not establish a voice/text shared-session contract. [source: S3, S7, S10, S11] (confidence: high; cited)

### Existing assessment and feature work

- **Feature 006 directly overlaps part of this idea.** Its research records a prior requester decision to keep working-agent instructions out of the speaking model, while giving that model a quiet active-agent/reachable-community note. FR-014 and FR-038 capture those requirements. Tasks T042, T046 and T047 remain unchecked, and current composition still supplies the active agent prompt rather than the specified service-wide instructions and context-note flow. These are existing plans, not proof of an implemented fix. [source: S2, S9] (confidence: high; cited)
- **That planned note is not a complete conversation-progress record.** Its specified contents are the active agent's name/role and reachable communities' routing descriptions; it explicitly excludes agent instructions and layers. It does not specify forwarding every spoken exchange to the working agents. This limits what the existing feature can be claimed to address without further evidence. [source: S9] (confidence: high; cited)

### External precedents

- **Client delegation explicitly assigns context ownership to the application.** Both OpenAI and Azure Foundry document that client-delegation events contain metadata rather than task text, and that transcript events plus application state are needed to prepare backend work. OpenAI also describes custom routing between services/agents as an application responsibility. This corroborates the local trace: using the same model/agent registry does not automatically supply the ongoing Live conversation to it. [source: E1, E2] (confidence: high for the documented contract; cited)
- **Managed Responses delegation is a documented alternative, not a demonstrated drop-in repair.** Both providers contrast application-owned client context with Live-prepared context for a configured Responses backend. They still assign permissions, confirmations and authoritative task state to the application. Nothing in that comparison proves compatibility with this repository's directed graph, filtered transfers, admission checks or current shared executor. [source: E1, E2, S6] (confidence: high for the alternative's existence; medium for the compatibility limitation; cited inference)
- **Agents SDK handoffs separate control transfer from context selection.** SDK documentation says a normal handoff gives the receiving agent conversation history unless an input filter or history mapping changes it. Handoff argument metadata is not a replacement for the receiving agent's main input and does not select another destination. This is useful prior art, but the repository disables SDK-native handoffs and instead implements its own authorization and context filtering. [source: E3, S6] (confidence: high; cited)

## Market & Context

- **This is an established orchestration concern, not evidence of unique demand.** OpenAI and Microsoft explicitly document the choice between managed backend context and application-owned context/routing; the Agents SDK independently documents history filtering at handoff. These sources establish available platform patterns, not market size, competitor outcomes or adoption by this repository's users. [source: E1, E2, E3] (confidence: high; cited)

These are observed application mechanisms, not confirmed workarounds chosen by affected users. [source: S3, S4, S5, S7] (confidence: high; cited)

## Data & Constraints

- **Context availability and authorization are different concerns.** Destination selection is constrained by protected roles, directed same-community agent edges, Routing-mediated community transfers, source epochs and permitted context fields. More context cannot itself grant an otherwise forbidden handover or capability. [source: S3, S6, S11] (confidence: high; cited)
- **Full conversation visibility is not the current privacy contract.** Voice content remains volatile; persistent text history is an explicit exception. Telemetry excludes conversation text, transcripts, prompts and tool payloads. Communities enforce discovery/context boundaries. Disclosure, consent, residency, retention and provider handling still need accountable-owner approval; this research establishes no jurisdiction-specific compliance conclusion. [source: S10, S11] (confidence: high for repository policy; cited)
- **Local bounds are material.** Executor aggregate retained context is capped at 256 KiB and speech transcripts at 64 KiB; the fragment correlator is capped at 4 KiB. Work is capped at eight counted steps, with default accepted-work budgets of 10 seconds for text and 30 seconds for speech, further capped by session/authentication limits. Socket replacement and routing consume the same accepted work budget. These are local controls, not provider capacity guarantees. [source: S3, S5, S6, S12] (confidence: high; cited)
- **Provider and local limits must not be conflated.** Current OpenAI guidance permits startup text history of up to 128 messages and 8,192 combined tokens, and describes append content up to 500 tokens. Azure also describes 500-token appends. This repository's adapter instead enforces a stricter 500-UTF-8-byte append and a 16-KiB instruction bound. No claim is made here that the deployed Foundry version accepts every option in current public guidance. [source: E2, E4, S2] (confidence: high for published/local limits; medium for deployed applicability; cited)
- **Context delivery is not proof of model uptake or audible delivery.** Platform guidance says append acknowledgements concern estimated context injection and do not prove the model used or spoke the information. Backend completion is also separate from what the caller heard. Consequently, a history of generated backend answers alone is not evidence of the exact audible conversation. [source: E1, E2, E4] (confidence: high; cited)
- **No reliable impact or cost baseline is available.** The capacity document leaves actual model cost, voice-context usage, live latency and capacity measurements pending. The intake adds no handover-correctness measurements. The focused local test run below confirms mechanics against doubles, not live routing quality or context-dependent conversational accuracy. [source: S1, S13, S14, V1] (confidence: high about the evidence gap; cited)

## Evidence Against the Idea

- **Against treating this as absent handover support:** the shared runtime already performs allowed handovers, rejects stale/forbidden transitions, and preserves filtered transfer context; targeted tests pass. The unsupported part is sufficient conversation awareness and decision quality in the reported scenario, not the existence of multi-agent transitions. [source: S6, S8, V1] (confidence: high; cited)
- **Against indiscriminate full-history sharing:** the existing destination-context restriction is intentional and explicitly tested. Expanding every agent's visibility could contradict that contract even if it made some ambiguous requests easier to interpret. [source: S3, S6, S8, S11] (confidence: high for the restriction; medium for the potential conflict; cited inference)
- **Against duplicating existing work:** feature 006 already specifies voice-model instructions and active-agent/reachable-community context. Some of the request overlaps unfinished work; the evidence does not establish that a separate broad feature is necessary rather than a narrower uncovered requirement. [source: S9] (confidence: medium; cited inference)
- **Against assuming more context alone fixes the complaint:** the trace also exposes a self-contained-fragment clarity gate, policy-constrained destinations, and voice-session replacement. No failing trace identifies which mechanism actually caused the reported wrong-agent experience. Giving a model additional information does not override those separate controls or prove correct use of it. [source: S2, S3, S5, S6, E4] (confidence: medium; cited inference)
- **Against assuming a broad rebuild is justified by demand:** there is one qualitative report and no measured prevalence, quantified harm, comparative evaluation or deployed reproduction. Current evidence supports investigating the gap, but cannot establish the value or required extent of a rebuild. No go/no-go decision is made here. [source: S1, S13, V1] (confidence: medium; cited inference)
